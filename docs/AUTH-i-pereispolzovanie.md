# «Наведи и убери»: двухуровневая авторизация и переиспользование Twin Things

Разбор ТЗ приложения «Наведи и убери» с точки зрения того, что уже готово и
проверено в **Twin Things**. Три части:

1. **Двухуровневая авторизация «пользователь → семья» по коду** — как в Twin
   Things; готовые правки в §3 и §10 ТЗ.
2. **Что переиспользовать** из кода Twin Things (модуль → применение).
3. **Архитектурные улучшения и упрощения.**

Ссылки на код Twin Things даны как `путь:строка`, чтобы можно было открыть
оригинал.

---

## Часть 1. Двухуровневая авторизация «пользователь → семья» по коду

### 1.0. Что не так с авторизацией в текущем ТЗ

Текущее ТЗ описывает **ровно три захардкоженных аккаунта в одной неявной
семье** (§3, §127). «Семья» нигде не является документом — она подразумевается.
Из-за этого:

- обещание из §168 «можно добавить четвёртое устройство без миграций» ничем не
  обеспечено: добавлять некуда, семья не выражена данными;
- §169 вычёркивает «семейный код» целиком — но вместе с ним уходит и способ
  привязать второго взрослого (второй родитель, телефон бабушки, второй дом при
  раздельном проживании) без ручной правки базы;
- «семья» как область видимости правил (`families/{familyId}` в §153) уже
  фигурирует в правилах, но не имеет ни жизненного цикла, ни владельца, ни
  способа в неё вступить.

Twin Things ровно эту задачу уже решил — только «семья» там называется
**каталог**, и связь пользователь↔каталог — **many-to-many** (один человек в
нескольких каталогах, в каждом своя роль). Берём эту модель как есть и адаптируем
роли под `parent`/`child`.

### 1.1. Примирение с детским UX: код — для взрослых, не для детей

Главное опасение ТЗ («семилетний ребёнок не будет вводить код/email») остаётся
верным и **никак не нарушается**. Разделяем два пути входа в семью:

| Кто | Как попадает в семью |
|---|---|
| **Первый родитель** | Регистрируется (email/пароль) → семья создаётся авто-матически, он её `owner`/`parent`, получает `joinCode`. |
| **Второй взрослый** (второй родитель, бабушка, второй телефон) | Вводит `joinCode` один раз → становится ещё одним `parent`-членом. Без миграций. |
| **Ребёнок** | Аккаунт создаёт родитель со своего телефона (как в §141). Ребёнок код **не вводит никогда** — только аватар + PIN на своём планшете. |

То есть §169 переформулируется не как «кода нет», а как «**код есть, но он для
взрослых устройств; дети им не пользуются, привязки устройств по-прежнему нет**».
Детский UX (аватар + PIN, `browserLocalPersistence`, вход один раз) не меняется
ни на строку.

### 1.2. Модель (уровень 1 — пользователь, уровень 2 — семья)

Прямая калька с `js/store.js:1-10` и `js/catalog-core.js:1-6`, `catalog → family`:

```
users/{uid}                       — профиль {displayName, email, createdAt}
users/{uid}/families/{fid}        — индекс «мои семьи» {role, name, joinedAt}   ← денормализация
families/{fid}                    — {name, ownerUid, joinCode, createdAt}
families/{fid}/members/{uid}      — ИСТОЧНИК ПРАВ {role: 'parent'|'child', addedBy, joinedAt}
families/{fid}/profiles/{profileId}          (profileId == uid ребёнка — §394)
families/{fid}/profiles/{profileId}/progress/{sessionId}
families/{fid}/profiles/{profileId}/rewards
families/{fid}/reference/{surfaceId}         — эталонные фото
families/{fid}/cards/{cardId}                — коллекция
families/{fid}/home, /settings               — карта дома, плейлисты, бюджет
```

Две вещи, которые отличают эту схему от Twin Things, и обе — сознательные:

- **`members` как источник прав, а не поле-map.** ТЗ §390 предлагает
  `members: { <uid>: 'parent'|'child' }` прямо в документе семьи. Twin Things
  держит `members/{uid}` **подколлекцией** (`js/store.js:8`). Подколлекция нужна
  здесь потому, что права должны гранулярно проверяться в правилах на **своём**
  профиле ребёнка (см. 1.4); map в документе семьи это выразить не даёт и на
  каждое изменение членства переписывает весь документ семьи. Рекомендация:
  **подколлекция**, как в Twin.
- **Роль ребёнка сужена до своего профиля.** В Twin любой член (`editor`) правит
  **весь** каталог. Здесь `child` — это `editor`, запертый в
  `profileId == uid`. Это единственная содержательная правка правил.

### 1.3. Роли: `parent` / `child` вместо `owner` / `editor`

`js/catalog-core.js:8-23` переносится один-в-один, меняются только имена и одно
доп. ограничение:

| Twin | «Наведи и убери» | Может |
|---|---|---|
| `owner` | `parent` | Всё в семье: дом, награды, эталоны, настройки, **оба** профиля детей, управление членами, `joinCode`. |
| `editor` | `child` | Только **свой** профиль: прогресс, награды, камера. Ничего чужого — ни в UI, ни в базе. |

`canEditItems`/`canManageCatalog` (`catalog-core.js:16-23`) → `canManageFamily(role)
= role === 'parent'`.

### 1.4. Правила безопасности (revised §10 → firestore.rules)

Берём каркас `firestore.rules:9-62` Twin Things и добавляем **один** match для
профиля ребёнка со сужением `profileId == uid`:

```js
match /databases/{database}/documents {
  function signedIn() { return request.auth != null; }
  function uid() { return request.auth.uid; }

  match /users/{u} {
    allow read, write: if signedIn() && u == uid();
    match /families/{fid} { allow read, write: if signedIn() && u == uid(); }
  }

  match /families/{fid} {
    function isMember() { return exists(/databases/$(database)/documents/families/$(fid)/members/$(uid())); }
    function role()     { return get(/databases/$(database)/documents/families/$(fid)/members/$(uid())).data.role; }

    allow read:   if isMember();
    allow create: if signedIn() && request.resource.data.ownerUid == uid();
    allow update, delete: if isMember() && role() == 'parent';

    match /members/{m} {
      allow read: if isMember();
      // Первый родитель записывает себя; дальше членами управляет только parent.
      // (Второго взрослого по коду добавляет Worker — см. Часть 3, п.1.)
      allow create: if signedIn()
        && (m == uid() && request.resource.data.role == 'parent'
            && get(/databases/$(database)/documents/families/$(fid)).data.ownerUid == uid())
        || (isMember() && role() == 'parent');
      allow update, delete: if isMember() && role() == 'parent';
    }

    // Профиль ребёнка и ВСЁ под ним (progress, rewards):
    //   parent — всё; child — только свой профиль.  ← ключевое отличие от Twin
    match /profiles/{profileId}/{document=**} {
      allow read, write: if isMember()
        && (role() == 'parent' || profileId == uid());
    }

    // Общее на семью: члены читают, пишет только parent.
    match /home/{d}      { allow read: if isMember(); allow write: if isMember() && role() == 'parent'; }
    match /settings/{d}  { allow read: if isMember(); allow write: if isMember() && role() == 'parent'; }
    match /reference/{s} { allow read: if isMember(); allow write: if isMember() && role() == 'parent'; }
    match /cards/{c}     { allow read: if isMember(); allow write: if isMember() && role() == 'parent'; }
  }
}
```

Заметьте: **ребёнок физически не может ни прочитать, ни записать профиль
брата/сестры** — это правило базы, а не только интерфейса (ровно как обещает
§164). А поскольку `child` не может писать в `members` (первый clause требует
`role=='parent'`), ребёнок и не может подсунуть себя в чужую семью — детей всегда
провиженит родитель. Это даже строже, чем открытый join-по-коду в Twin.

Storage-правила — прямая калька `storage.rules` (файл виден тем, кто в
`members`), путь `families/{fid}/reference/{surfaceId}.jpg`:

```js
match /families/{fid}/{allPaths=**} {
  allow read, write: if request.auth != null
    && firestore.exists(/databases/(default)/documents/families/$(fid)/members/$(request.auth.uid));
}
```

### 1.5. Готовые правки в текст ТЗ

- **§3 «Авторизация»** — заменить абзац «Три аккаунта в одной семье» на
  двухуровневую модель из 1.2–1.3: пользователь (уровень 1) ↔ семья (уровень 2,
  документ с `joinCode`), many-to-many через `members`. Оставить как есть весь
  блок «Как это выглядит для ребёнка» и «Вход — один раз на устройство».
- **§169** — переформулировать: ~~«никакого семейного кода… этот кусок из ТЗ
  уходит»~~ → «семейный код остаётся, но только для добавления **взрослых
  устройств**; дети им не пользуются, привязки устройств по-прежнему нет».
- **§143** — «Отдельный PIN на взрослый раздел не нужен» — верно, оставить.
- **§10 модель данных** — заменить `members: { <uid>: … }` (map) на подколлекцию
  `families/{fid}/members/{uid}` и добавить индекс `users/{uid}/families/{fid}`
  (см. 1.2).
- **§166 «что даёт нормальная авторизация»** — пункт «добавить четвёртое
  устройство без миграций» теперь действительно обеспечен кодом, а не декларация.

## Часть 2. Что переиспользовать из Twin Things

Twin Things — то же «семейство Twin»: статическое PWA без сборки (vanilla ES-
модули), **отдельный** Firebase-проект (Auth + Firestore + Storage), GPT-4o через
Cloudflare Worker. Стек ТЗ совпадает **дословно** (§106–123), поэтому
переиспользование — не «вдохновиться», а «скопировать файл и переименовать».

### 2.1. Копируется почти как есть

| Twin Things | В «Наведи и убери» | Что делать |
|---|---|---|
| `js/catalog-core.js:29-34` `makeJoinCode`/`normalizeJoinCode` (алфавит без I/L/O/0/1) | `joinCode` семьи | скопировать дословно |
| `js/catalog-core.js:38-46` `makeCatalogId` (слаг + случайный хвост) | `makeFamilyId`, `makeSurfaceId`, `sessionId` | скопировать, переименовать |
| `js/catalog-core.js:51-55` `pickActiveCatalog` + `ACTIVE_KEY` (`store.js:25,117-125`) | активная семья (у родителя их может быть >1: свой дом + второй дом) | скопировать |
| `js/catalog-core.js:8-23` роли/`isValidRole`/`canManage*` | `parent`/`child` | скопировать, переименовать роли |
| `js/store.js:31-106` блок авторизации: `initAuth`, `signInEmail`, `ensureUserDoc`, `POPUP_FALLBACK`, redirect-fallback | вход родителя + восстановление сессии | скопировать; поверх добавить обёртку «аватар+PIN» для детей |
| `js/store.js:110-179` many-to-many: `listMyCatalogs`/`createCatalog`/`joinCatalogByCode`/`ensureFirstCatalog` | `listMyFamilies`/`createFamily`/`joinFamily`/`ensureFirstFamily` | скопировать, `catalog→family`, join → в Worker (Часть 3, п.1) |
| `firestore.rules` (isMember/role/бутстрап первого владельца) | правила семей | скопировать + профиль-скоуп (1.4) |
| `storage.rules` (Storage читает членство из Firestore) | эталонные фото | скопировать, путь `families/{fid}/reference/**` |
| `js/firebase.js` инициализация (Auth+Firestore+Storage, `authReady`) | то же | скопировать; добавить `browserLocalPersistence` (нужно для «вход один раз», §139) |
| `js/image.js` `compressForUpload` (canvas: основное ~1600px + превью ~300px) | сжатие эталонов; подготовка кадра для `/scan` (1024px, q0.7 — §228) | переиспользовать пайплайн, поменять целевой размер |
| `js/ai.js:11-20` `gpt()` — вызов через Worker; `parseAiJsonArray/Object`, `sanitizeAiItems` (`catalog-core`) | `/scan` `/verify` `/parse-home` `/reward` | переиспользовать: «отвечать только JSON + один повтор при невалидном + санитайз» — это ровно требование §442 |
| Worker `/ai` (прокси OpenAI, проверка Origin, ключ на стороне воркера) | добавить маршруты `/tidy/*` | тот же воркер (§18, §173): новые маршруты под префиксом `/tidy/`, лимиты по `deviceId` |
| `pwa.js`/`sw.js`/`manifest.json` | PWA на планшетах | скопировать оболочку |
| Дизайн-система `styles.css` на CSS-переменных | две темы minion/jedi | переиспользовать **архитектуру переменных**: тема = один набор значений переменных (ровно как в §42-47) |
| `docs/PLAN.md` (разработка волнами) + `tests/*.test.mjs` (`node --test`, чистые модули без Firebase) | та же дисциплина | держать `*-core.js` чистыми и тестируемыми без Firebase — сразу переносится на `/parse-home`, `/scan`, цветовой словарь, логику наград |

### 2.2. С оговорками

- **`voice.js` — это распознавание речи (вход), а ТЗ нужна озвучка (выход).**
  `voice.js:34` использует `SpeechRecognition`; «озвучка каждого задания» (§29,
  §374) — это `speechSynthesis` (другой Web Speech API). Прямо не переносится.
  Полезен как **референс локали RU/переключателя языка** (`voice.js:10-33`) —
  пригодится, когда добавите шведский (§13).
- **Санитайзеры AI под другую схему.** `sanitizeAiItems` заточен под вещи
  каталога; для `/scan`/`/verify` нужны свои валидаторы под форматы §246, §276,
  §292. Но **паттерн** (строгая JSON-схема → парс → один retry → санитайз →
  фолбэк) переносится дословно — это самое ценное.

## Часть 3. Архитектурные улучшения и упрощения

### 3.1. Join-по-коду делать в Worker, а не на клиенте (важно)

**Находка в Twin Things:** клиентский `joinCatalogByCode` (`store.js:155-171`)
**конфликтует с его же правилами**. Не-член не может:
1. выполнить `query(catalogs where joinCode==code)` — `read` требует `isMember()`
   (`firestore.rules:31`);
2. записать себя в `members` — `create` для не-owner требует уже быть
   `role()=='owner'` (`firestore.rules:39-42`).

То есть join-по-коду в Twin работает только в test-mode (открытая база). Это
классический тупик «invite-code в client-side rules»: чтобы найти семью по коду,
надо её прочитать, а прочитать может только член.

**Решение для нового приложения (воркер уже есть):** маршрут
`POST /tidy/join { code }` с проверкой Firebase ID-token. Воркер на Admin SDK
валидирует код и **сам** пишет `members/{uid}` + `users/{uid}/families/{fid}`.
Плюсы: код не читается клиентом, правила остаются закрытыми, второй родитель
добавляется одним запросом. Детей провиженит родитель напрямую (он уже `parent`,
правила это разрешают) — воркер для детей не нужен.

### 3.2. Упрощение: убрать custom claims, роль брать из `members`

§135 предлагает хранить роль **и** в custom claims токена, **и** в документе.
Custom claims требуют Admin SDK для записи и **обновления токена** для
распространения — это гонки (создали ребёнка → его токен ещё старый) и лишняя
движущаяся часть. Twin Things обходится **без claims**: роль выводится в правилах
через `get(.../members/$(uid())).data.role` (`firestore.rules:27-29`). Одна
запись правды вместо двух. Плата — один лишний read документа членства на
проверку; Twin показывает, что это приемлемо. **Рекомендация: отказаться от
custom claims, оставить только `members`-документ.**

### 3.3. `profileId == uid` — оставить как в §394

ТЗ уже принял верное решение: `profileId == uid` ребёнка, «правила проверяются в
одно сравнение». Это ровно то, на чём стоит скоуп-правило 1.4
(`profileId == uid()`). Ничего менять не надо — просто отметить, что это несущая
конструкция, а не оптимизация.

### 3.4. Один «активный контейнер» вместо привязки к устройству

ТЗ §169 отказывался от «привязки устройств». Правильно — но тогда нужен способ
понять, «в какой семье сейчас этот телефон». Twin решает это без привязки:
`activeCatalogId` в `localStorage` + `pickActiveCatalog` (`store.js:117-125`,
`catalog-core.js:51-55`). Родитель с двумя семьями переключается свитчером; у
ребёнка семья одна, свитчер скрыт. Переиспользуется как есть.

### 3.5. `members`: подколлекция, не map (см. 1.2)

Итог: `families/{fid}/members/{uid}` подколлекцией (Twin), а не
`members: {uid: role}` map в документе (текущий §390). Причины — гранулярные
правила на профиле и отсутствие перезаписи всего документа семьи при каждом
изменении членства.

### 3.6. Единый пайплайн фото для эталонов и `/scan`

`image.js` уже умеет «canvas → сжать → JPEG». ТЗ требует то же в двух местах:
эталонные фото (§300) и кадр для `/scan` (1024px, q0.7, проверка яркости §470).
Сделать **один** модуль `image-core.js` (чистый, тестируемый — как в Twin) с
параметром целевого размера, а проверку яркости добавить туда же перед отправкой.
Не плодить два пути сжатия.

### 3.7. Денормализация имени — тот же приём, те же грабли

Twin денормализует имя каталога в индекс `users/{uid}/catalogs` и при
переименовании пишет **в оба места** (`store.js:183-189`). В новом приложении имя
семьи и (возможно) имя/аватар профиля денормализуются так же — заложите парную
запись сразу, иначе имена разъедутся.

### 3.8. Что можно НЕ строить на этапе 1

- **`viewer`-роль** — в Twin отложена (Wave 5). Здесь для этапа 1 достаточно
  `parent`/`child`; «только смотреть» не нужен.
- **email-приглашения** (`invites/*`, `firestore.rules:47-50`) — в Twin это
  Wave 2. Для семьи из 3-4 человек хватает `joinCode`; полноценные приглашения по
  email не нужны, пока не решите «расшаривать» семью наружу.

## Итог одним абзацем

Двухуровневая модель «пользователь → семья по коду» из Twin Things переносится в
«Наведи и убери» почти дословно (`catalog → family`, `owner/editor →
parent/child`), добавляя ровно одно правило — сужение ребёнка до своего профиля
(`profileId == uid`). Код, роли, id, активный контейнер, правила членства,
Storage-доступ, инициализация Firebase, пайплайн фото, паттерн вызова AI через
Worker и дисциплина «чистое ядро + Node-тесты» берутся из готовых файлов. Три
содержательных улучшения: **join-по-коду в Worker** (клиентский путь в Twin
ломается о собственные правила), **отказ от custom claims** в пользу единственного
`members`-документа, и **подколлекция `members`** вместо map ради гранулярных
правил на профиле ребёнка.
